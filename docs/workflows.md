# ClipLayer 主要ワークフロー

ユーザー（非エンジニア）が触れる 3 つの主要 GUI ワークフローを定義する。**コードを書く操作は一切不要** が共通の必須要件。

---

## Flow A: 公式 profile を使ったデータ取り込み

### 想定シナリオ
楽天 RMS の注文一覧から、毎日の注文データを Slack に流したい店長。

### ステップ

```
1. ClipLayer 拡張機能をインストール
2. Side Panel を開く → ログイン
3. Profile タブで「楽天 RMS 注文一覧」を見つけて「導入」
4. 楽天 RMS にいつも通りログインし注文一覧ページを開く
5. Side Panel に「このページから取り込み可能」バッジが出る
6. 「実行」押下 → 24 件抽出 → Slack に送信
7. 履歴タブで結果確認
```

### 画面遷移

```
[Side Panel: このページ]
┌─────────────────────────────────┐
│ ✓ 楽天 RMS 注文一覧 v8 公式      │
│   推定 24 件                     │
│                                   │
│ プレビュー（最初の 3 件）         │
│ ┌─────────────────────────────┐│
│ │ 1001 山田... 5/19 ¥12,000   ││
│ │ 1002 佐藤... 5/19 ¥8,400    ││
│ │ 1003 鈴木... 5/19 ¥15,200   ││
│ └─────────────────────────────┘│
│                                   │
│ 送信先: Slack #orders             │
│ ☑ ローカル保存も併用              │
│                                   │
│ ▶ 取り込み実行                    │
└─────────────────────────────────┘
```

### 内部処理

```typescript
// 擬似コード
on click "実行":
  run = await runsRepo.start(profile.id)
  result = await sendToContent(tabId, { type: "EXTRACT", profileId })
  await pipeline.persist(run.id, result)
  if (profile.delivery) await delivery.send(profile.delivery, result)
  await runsRepo.complete(run.id, result)
```

### 重要 UX
- 「実行」前に必ずプレビューを表示する（爆弾を踏ませない）
- 送信先の設定は profile に紐付け（毎回選ばせない）
- 失敗時は理由を日本語で明示

## Flow B: 自社サイトのセレクタを GUI で登録（Element Picker）

### 想定シナリオ
自社の予約管理画面から、毎日の予約一覧を CSV で出力したい店長。

### ステップ

```
1. 自社の管理画面を開く
2. Side Panel「+ 新規 Profile」
3. プロファイル名入力: "予約管理 - 当日分"
4. URL パターン選択:
   ● このページのみ
   ○ このパス配下
   ○ このドメイン全体
5. 「ピックモード開始」
6. ページ上に半透明オーバーレイ + 指示パネル表示
7. リスト行（予約 1 件分）を 1 クリック
8. システムが「12 件の繰り返し要素を検出」→ ハイライト
9. 「これで合っていますか？」
   ● はい / ○ もっと外側 / ○ やり直す
10. はい → フィールド指定モードへ
11. 「顧客名」要素をクリック → ラベル「customer_name」入力
12. 「予約日時」要素をクリック → ラベル「reserved_at」入力
13. ... 必要なフィールドを順次追加
14. リアルタイムプレビューで全 12 件の抽出結果が見える
15. 「完了」押下
16. 「送信先」設定: CSV ダウンロード / Webhook / なし
17. 「保存」→ Profile 完成
```

### Element Picker の UI

```
ページ上に注入される overlay (Shadow DOM):

┌─────────────────────────────────────────────┐
│ ClipLayer Picker                       [×]  │
├─────────────────────────────────────────────┤
│ Step 2 / 3: フィールドを指定                │
│                                               │
│ クリックして値を取得する要素を選択           │
│                                               │
│ 取得済みフィールド:                          │
│  ✓ customer_name  (山田太郎)                 │
│  ✓ reserved_at    (2026-05-20 19:00)         │
│  ✓ phone          (090-...)                  │
│                                               │
│ プレビュー（12 件中 3 件表示）               │
│ ┌─────────────────────────────────────────┐│
│ │ 山田 / 5/20 19:00 / 090-1111-2222       ││
│ │ 鈴木 / 5/20 19:30 / 090-3333-4444       ││
│ │ 佐藤 / 5/20 20:00 / 090-5555-6666       ││
│ └─────────────────────────────────────────┘│
│                                               │
│ [ 戻る ]  [ 完了 ]                          │
└─────────────────────────────────────────────┘
```

技術仕様の詳細は [element-picker.md](element-picker.md) を参照。

### 重要 UX
- リスト検出の精度が UX を支配する。手動で「もっと外側 / 内側」に調整できる退路必須
- 安定セレクタ生成は `data-*` → `role` → 親階層 + nth-of-type の優先順
- プレビュー件数は 3〜5 行に絞り、件数が多くても重くならないようにする
- 編集モードでセレクタを後から直接書ける（パワーユーザー向け）

## Flow C: 公式 profile の自動更新

### 想定シナリオ
楽天 RMS が DOM を変えた日、ユーザーが気づく前に直っていてほしい。

### バックグラウンド処理

```
1. インストール時 + 24h ごと + 起動時に sync 起動
2. background → サーバ /profiles GET (plan ヘッダ送信)
3. 各 profile の署名検証（Ed25519 公開鍵は拡張に同梱）
4. ローカル version < サーバ version → upsert
5. 更新があった profile を logs に記録
6. Side Panel が開いていれば「更新あり」バナー
```

### 破損検知 → 即時 sync

```
1. ユーザーが実行
2. 抽出失敗（必須フィールド欠落 or item 数 0）
3. background が profile.brokenSince = now() でマーク
4. サーバに POST /profiles/:id/report-broken（URL, errors）
5. 即 sync 起動 → 新版があれば適用
6. 「自動修正中... ETA 24h」と UI 表示
7. サーバ運営側がアラート受信 → 修正 publish
8. ユーザーの次の起動 / 次の sync で新版受信 → 自動復旧
```

### 通知の見せ方

```
[Side Panel: Profiles タブ]
┌─────────────────────────────────────┐
│ 🔔 12 個の Profile が更新されました   │
│                                       │
│ 🟢 楽天 RMS 注文一覧                 │
│    v7 → v8 に更新                    │
│    変更内容: 注文ID列のセレクタ修正  │
│                                       │
│ 🟡 Amazon Seller 在庫                │
│    v5 から壊れています               │
│    自動修正中... ETA 24h             │
│    [一時無効化]                       │
└─────────────────────────────────────┘
```

### 重要 UX
- 「自動で直る」体験を演出する。ユーザーが手を動かさずに復旧することがサブスクの体感価値
- 破損中の profile は実行ボタンを非活性化し、誤ってボタン押下→失敗を防ぐ
- 更新内容（changelog）を 1 行で明示し、変更を知らせる

## 共通 UX 原則

### 1. 失敗を隠さない
- 抽出失敗・送信失敗は明確に表示し、再実行ボタンを提供
- 「とりあえず成功表示」は UX 上最悪

### 2. プレビュー必須
- 「実行前に何が起きるかが見える」を必須要件にする
- profile 編集中もリアルタイム反映

### 3. 取り消し可能性
- profile 削除は trash に入れ、30 日復元可能
- 履歴の手動削除も同様

### 4. 必要最小限の選択肢
- 「URL パターン」は 3 択（このページ / パス配下 / ドメイン全体）
- 「フィールド型」は 4 択（text / attr / html / image-url）
- 高度な設定は折り畳んで隠す

### 5. 非エンジニアへの言葉遣い
- 「セレクタ」「DOM」などの技術語は UI から避ける
- 「取り出したい項目」「クリックして指定」など平易な表現
- 例外: 高度な設定タブ内では正確な技術語を使う

## ワークフロー間の繋がり

```
[Flow A: 公式利用]  ──┐
                      │
[Flow B: 自作]    ────┼──→ 取り込み実行 ──→ 送信先 ──┐
                      │                                │
[Flow C: 自動更新] ───┘                                ▼
                                                  [履歴・分析]
                                                       │
                                                       ▼
                                          [次の実行 / トラブル対応]
```

3 つのワークフローを行き来する設計だが、初回ユーザーは Flow A から入る。Flow B は中級ユーザー、Flow C はバックグラウンドで自動。

## ワークフローと plan の対応

| ワークフロー | Free | 有料 ¥700/月 |
|---|:---:|:---:|
| Flow A（公式 profile 利用） | × | ◯ 全サイト |
| Flow B（自作 profile） | 1 枠 | 無制限 |
| Flow C（自動更新・破損検知） | 受信不可 | 受信可 |
| 動的ページ巡回（list → detail）| × | ◯（Phase 8 から）|
| 送信先 Webhook | ◯ | ◯ |
| 送信先 CSV | ◯ | ◯ |
| デバイス数 | 1 | 3 |

Free は「自作 profile 1 個・自分で書ける人向け・布教用」と位置付ける。AI 解析・クラウド同期は MVP では提供しない。動的ページ巡回（list → detail）は仕様確定済みだが MVP では未実装で、Phase 8 で追加（[dynamic-traversal.md](dynamic-traversal.md) 参照）。
